# Атомарные продажи и кассовые операции

## Как установить обновление

1. Сделайте резервную копию рабочей базы и убедитесь, что предыдущие миграции
   проекта (до v44 включительно) применены. `client_op_id` должен иметь тип TEXT,
   как в v37; сами идентификаторы новых самостоятельных операций — UUID.
2. В Supabase SQL Editor повторно выполните обновлённый файл
   `supabase/v36_atomic_offline_sales.sql`. Его интерфейс не изменён; добавлено
   использование активного магазина при работе суперадминистратора.
3. Выполните `supabase/v45_atomic_cash_operations.sql`. Она создаёт новую RPC,
   SQL-агрегаты кассы и переводит выплаты поставщикам на тот же замок магазина.
   Миграция также уведомляет PostgREST об обновлении схемы.
4. Только после успешного выполнения SQL разверните новый код приложения.
   Production-сборка: `npm run build`; запуск: `npm start`. Сохраняйте прежний URL,
   если пользователи уже установили приложение как PWA.

Рабочая база при подготовке этого ZIP не изменялась. Файлы в `tests/` — только
тестовые схемы: **не запускайте их в рабочем Supabase**.

## Что изменилось

- `checkout()` вызывает `commit_offline_sale`, а не отдельные списания товаров
  и вставку чека. Конфликт остатков отклоняет весь чек. Создание клиента,
  статистика, склад и связанная кассовая запись выполняются внутри существующей
  SQL-транзакции. Повторные начисления из TypeScript удалены.
- Возвращаемые суммы читаются из уже подтверждённого чека, в том числе при
  `duplicate=true`, а не рассчитываются заново по изменившимся остаткам.
- `createCashOperation()` вызывает `create_cash_operation_atomic`. Проверка
  баланса и вставка выполняются в одной транзакции под замком
  `<shop_id>:cash-ledger`. Ранее использовавшиеся постраничные запросы удалены.
- SQL учитывает наличные, электронные средства, смешанную оплату, инкассацию
  как перемещение, мягкие удаления, старые чеки без разбивки и кассовые зеркала
  атомарных продаж — без двойного учёта выручки.
- Повторный `client_op_id` не списывает деньги ещё раз и не создаёт повторный
  шаблон причины. Использование того же ключа с другим кассовым payload
  отклоняется. Шаблон причины создаётся в той же транзакции.
- Кассовые операции из offline outbox тоже отправляются через новую RPC.
  Постоянно отклонённая операция сохраняется в outbox для проверки, а её
  предварительная локальная запись исключается из баланса.

## Правила повторной отправки

При первом вызове создавайте UUID на клиенте и передавайте `client_op_id`.
Повторяйте неопределённый запрос **с тем же UUID и теми же данными**.
В формах ключ сохраняется между попытками, пока форма открыта; быстрые двойные
нажатия блокируются. При изменении данных создаётся новый ключ. Offline outbox
хранит ключ в IndexedDB.

Для обратной совместимости серверная action создаст UUID, если его не передали,
но два отдельных вызова без ключа считаются разными операциями. После потери
ответа не закрывайте форму и не создавайте новую операцию, не проверив историю:
после закрытия/перезагрузки форма может создать новый ключ.

Advisory lock защищает операции, использующие этот же протокол: новую кассовую
RPC, offline `atomic_cash` и выплаты поставщикам. Он не является глобальным
ограничением произвольного прямого INSERT/UPDATE. Возвраты, отмены и двухшаговый
приём лома «создать товар + оплатить» не переделаны в единые новые транзакции.
Новые денежные записи следует создавать через RPC, а не напрямую из клиента.

## Проверки

После установки зависимостей: `npm run test:atomic`.
Проверяются повторы, потеря ответа, конфликт остатков, отсутствие ручных
денежных записей, валидация сумм и синтаксис изменённых TypeScript/TSX-файлов.

Для интеграционных тестов нужен отдельный локальный PostgreSQL, новая пустая
одноразовая база `aura_atomic_test` и пользователь, который может создавать
тестовые таблицы/роль. Пример для локального сервера:

```sh
createdb aura_atomic_test
PGDATABASE=aura_atomic_test npm run test:atomic:postgres
```

Скрипт отказывается работать с другим именем базы. Он создаёт тестовую схему,
загружает v36/v45 и проверяет SQL-транзакции, RLS, недостаток средств, повторную
отправку, более 1000 записей, откат при ошибке записи кассы и реальные
конкурентные запросы: два изъятия, два одинаковых запроса, изъятие одновременно
с выплатой поставщику и две продажи одного изделия.
Повторный запуск требует новой пустой тестовой базы.

Эти проверки не заменяют production-сборку и тесты на фактической схеме вашего
Supabase со всеми её триггерами и политиками.
